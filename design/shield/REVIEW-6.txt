REVIEW-6 — защита 1.2.3 (2e62399) и 1.2.4 статистика, шаг 1 (0d798e2 + f1f63b3)
Проверяльщик: Opus 5.5 xhigh, один проход, высокий риск. Ветка test-shield, worktree shield.
Строки — по go-installer.sh на f1f63b3. Эксперименты — на извлечённом коде _shield_spy (heredoc SPY),
Python 3.9 и 3.14, macOS; Lima не понадобилась.

ВЕРДИКТ: после правок (2 серьёзно; блокеров нет).

A) 1.2.3 «Список сервисов» (2e62399)

B) 1.2.4 статистика

1. СЕРЬЁЗНО — память и время снимка/отчёта на 200 тыс. адресов; на VPS 512 МБ — риск OOM, раскачивается извне.
   Где: go-installer.sh:5601 (MAXADDR = 200000), :5854 ld_rows (вся база addrs списком списков строк),
   cmd_snap :5906 (словарь A по всей базе, запись :6099), summary :6161 (в ветке без нового счёта :5927/:5940
   тоже читает всю базу), cmd_report :6334.
   Замер (синтетика: addrs 200 тыс. + листинг seen4 65536 со счётчиками, pair4 32768, ports 8192, scan4 30 тыс.):
     snap, новый ключ: 2,06 с CPU, maxRSS 384 МБ (py3.9); устойчивый снимок: 1,02 с / 288 МБ (3.9), 0,74 с / 268 МБ (3.14);
     report: 0,64 с / 253 МБ; для сравнения 50 тыс. — 84 МБ / 0,12 с, 20 тыс. — 47 МБ.
   Плюс листинг nft на таком наборе 2–2,8 с. Цель SPEC-stats «≤ ~1 с CPU на 200 тыс.» не выполнена; в отчёте
   исполнителя «разбор python 0,1–0,3 с» — не подтверждается.
   Раскачка: подменённые SYN из сетей списка заполняют seen4/seen6 (до ~80 тыс. новых адресов в час) — база
   доходит до 200 тыс. за ~3 ч. Снимок идёт не только раз в час, а при каждом shield_apply (:7071: включение,
   исключения, обновление списка, сторож SSH) — под замком, рядом с xray/awg на 512 МБ.
   Как чинить: не держать всю базу в памяти списками строк — потоковое слияние (addrs отсортирован → merge с
   новыми адресами), компактные записи (tuple/array, адрес как int), summary без загрузки addrs (нужные числа —
   в meta); и/или MAXADDR ≈ 50 тыс. Решение по лимиту — за владельцем, если меняется смысл «всех адресов».
   Как проверить: тест/скрипт с базой на лимит: /usr/bin/time -l (Linux: -v) для snap и report —
   maxRSS ≤ ~60 МБ, CPU ≤ ~1 с; в test_goinstaller.sh — раздел с большой базой (генератор) и порогом по RSS.

2. СЕРЬЁЗНО — ReDoS в cmd_owners на чужом списке сетей (зависание под замком на часы).
   Где: go-installer.sh:5722 — re.sub(r'\(\s*\)|\b[A-Za-z0-9-]+-MNT\b', ' ', m.group(2)) по строке без ограничения длины;
   файл списка до 8 МБ (:6829 max-filesize = 8000000).
   Воспроизведение: строка «# NET-Name: 45.0.0.0/16 » + «a-» * 40000 → `python3 spy.py owners …`: 10,5 с;
   голая регулярка 10к симв. 0,17 с, 20к 0,68 с, 40к 2,7 с (квадрат). 8 МБ одной строкой — часы.
   Идёт в shield_accept/tick под замком защиты; у oneshot-юнита нет TimeoutStartSec — тик стоит, списки и снимки
   не обновляются.
   Как чинить: резать до регулярки (m.group(2)[:400]) или пропускать строки длиннее ~1 КБ; регулярку без
   перекрытия (например, токенизировать split() и отбрасывать слова на -MNT).
   Как проверить: тест — список с одной строкой NET-Name на 8 МБ из «a-», owners завершается < 1 с, метка ≤ 60 симв.

3. ЗАМЕТНО — двойной счёт при сбое записи посреди cmd_snap.
   Где: :6088–6109 — hours/days/… пишутся по одному через os.replace, meta (key/база дельты) — последней.
   Если запись падает после hours/days (ENOSPC, OOM-kill на ~14 МБ addrs, EIO), meta остаётся старой,
   следующий снимок считает ту же дельту ещё раз.
   Воспроизведение (извлечённый spy, каталог addrs.tmp заменён на каталог): счётчик 100 → 150 → 200 со сбоем на
   addrs → повтор: tin=200, сумма hours=250, days=250.
   Как чинить: двухфазно — все .tmp сначала, затем os.replace подряд, meta последней; либо meta (с key/счётчиками)
   первой как журнал и идемпотентное применение.
   Как проверить: тот же сценарий (сбой на addrs, повтор) — сумма hours == tin == days.

4. ЗАМЕТНО — сводка при входе показывает устаревшие числа как «за сутки».
   Где: :13160 _shield_sum_load — возраст snap не проверяется. Если снимки встали (п.1 OOM, п.2, symlink stats/,
   ошибка python), motd бесконечно показывает последние числа «за сутки».
   Как чинить: now − snap > ~3 ч → блок не показывать или писать «нет свежих данных (снимок HH:MM)».
   Как проверить: тест — summary с snap=now−4ч → в выводе нет «за сутки»/есть пометка.

5. ЗАМЕТНО — полный листинг таблицы стал тяжёлым (до ~139 тыс. динамических элементов, 2–2,8 с).
   Где: :7117 shield_live_ok и :7597 shield_teardown — `nft list table` целиком; вызывается при открытии меню
   (:11636, а также :7798/:7836/:8236 shield_state --live) и в тике.
   Как чинить: `nft -t list table …` (terse, без элементов наборов) или листинг нужных цепочек/наборов по имени.
   Как проверить: на стенде с заполненными seen4/pair4 — `time` открытия меню/shield_live_ok < 0,3 с;
   в тесте фейковый nft проверяет, что вызывается с -t.

6. ЗАМЕТНО (вопрос владельцу) — разбивка «клиенты/сервер» вводит в заблуждение.
   Трафик клиентов VLESS/Xray (и прочих прокси на сервере) идёт через OUTPUT → считается «сервер», а не «клиенты»;
   «клиенты» = только FORWARD (WG/AWG/каскад). Разбивка взята из SPEC-stats, поэтому код не ошибка.
   Как чинить: формулировка — «через туннель (WG/AWG)» / «с самого сервера (в т.ч. VLESS)», или пояснение в отчёте.
   Как проверить: текст отчёта и сводки согласован с владельцем.

Проверено, дефектов нет:
 - порядок правил: SSH/allow/K3-5 не сдвинуты; jump в stat-цепочки после allow и до drop/reject, в stat-цепочках
   нет вердикта; счётчики vk после allow и до reject; уровни 3→0 через nft -c, откат на 0 одной транзакцией
   (table{} + delete + table{…}) — половинной таблицы нет; «сканеры выкл» = только счёт; при всём выкл таблица
   остаётся (SHS_ST=off);
 - дельты: ключ boot_id:handle — перезагрузка, пересборка, сброс дают новый ключ без двойного счёта (кроме п.3);
 - stats/: wr() через .tmp с O_NOFOLLOW + os.replace, SHIELD_DIR 0700 root; сохраняется через
   self_install/update/apply/remove, удаляется при uninstall вместе с GOINST_DIR;
 - motd: только bash, читает stats/summary и stats/seen, без сети и python; ключи printf -v фиксированные;
   метки AS чистятся (печатные, без Cc/Cf/bidi, ≤60), ui_padr/ui_fit режут; «пока вас не было» по seen;
 - тексты RU/EN, подвал отчёта по брифу, коды выхода --shield stats.

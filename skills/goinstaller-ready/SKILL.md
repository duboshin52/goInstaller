# Как оформить продукт, чтобы его понимал goInstaller

goInstaller ничего не настраивает сам. Он проверяет машину, называет
занятые порты, спрашивает ветку и передаёт управление **штатному
установщику продукта**. Всё, что ему нужно от продукта, перечислено ниже.
Нарушение любого пункта не ломает продукт, но делает его невидимым или
опасным для соседей по серверу.

Правила выведены из шести продуктов и трёх живых серверов. У каждого
указано, чем платят за нарушение.

## 1. Версия: одна переменная, начало строки

Объявите версию так, чтобы её можно было прочитать **и на сервере, и в
ветке на GitHub одной и той же командой**:

```bash
GOPRODUCT_VERSION="1.4.2"
```

- Имя переменной заканчивается на `_VERSION`, только заглавные, цифры и
  подчёркивание.
- Присваивание стоит **в начале строки**. Упоминание в комментарии или
  внутри `echo` версией не считается и прочитано не будет.
- Значение начинается с цифры и сравнивается через `sort -V`. `0.10.0`
  новее `0.9.0`, и это работает только при таком формате.
- Лежит в `lib/common.sh`, а у однофайловых продуктов в самом файле.
  goInstaller ищет по очереди: `lib/common.sh`, `install.sh`,
  `bootstrap.sh`, `<продукт>.sh`, `warp.sh`.

**Поднимайте версию при каждом пуше.** goInstaller показывает оператору то,
что объявлено в ветке. Продукт, забывший поднять переменную, выглядит
устаревшим, а его обновление — бессмысленным. Ошибка не видна никому,
кроме покупателя.

## 2. Ветки: ровно две

`main` — стабильная, `dev` — экспериментальная. Оператору предлагаются
только они, остальное считается рабочими ветками автора.

- Наличие ветки проверяется у GitHub при запуске, поэтому продукт без
  `dev` просто покажет одну строку. Заводить пустую ветку ради вида не
  надо.
- Рабочие ветки называйте как угодно: `rc1`, `alfa-v2`, `claude/*`,
  `backup/*`. В выбор они не попадут.
- **Загрузчик обязан уметь сменить ветку у уже установленного.** Это
  главный сценарий: человек переезжает с dev на main и обратно. Проще
  всего качать срез ветки архивом по хешу коммита, как goTelegram pro,
  goDNS pro и goAmnezia pro: каждый запуск кладёт свежее дерево выбранной ветки. Если
  код лежит git-клоном, не клонируйте одну ветку (`clone -b … --depth 1`
  создаёт клон, который другую ветку не видит) или сразу разрешите ему
  все ветки: `git config remote.origin.fetch '+refs/heads/*:refs/remotes/origin/*'`.
  goVLESS pro на этом попался: печатал «✓ Updated to latest dev» и оставался
  на main, потому что ошибки checkout и reset глушились `|| true`.
  После переключения сверяйте `git rev-parse --abbrev-ref HEAD` и версию,
  а не печатайте успех.
- Ветка по умолчанию репозитория должна быть `main`. Если её нет, а есть
  только `dev`, установщик это переживёт, но команда установки из вашего
  README будет врать.

## 3. Репозиторий и точка входа

- Репозиторий **приватный**, читается тем же ключом, что и остальные.
  Ключ выдаётся подписчикам в клубе, ветка `goinstall`.
- В корне лежит исполняемый файл-загрузчик: `bootstrap.sh` или
  `install.sh`. Первая строка — shebang `#!/bin/bash`. goInstaller
  проверяет её и отказывается запускать то, что не похоже на скрипт: так
  ловится страница ошибки, прилетевшая вместо файла.
- Загрузчик обязан работать через `curl` с заголовком авторизации, без
  `git clone`: на чистой машине git может отсутствовать, а приватный
  клон попросит логин и повиснет.
- **Качайте по хешу коммита, а не по имени ветки.** У
  `raw.githubusercontent` на URL ветки свой кэш на пять минут: сразу
  после пуша он отдаёт прежний файл, и установщик молча ставит старую
  версию, сообщая новую. Это ловилось вживую на самом goInstaller.
  Порядок такой: спросить `api.github.com/repos/<репо>/commits/<ветка>`,
  взять `sha`, качать `raw.githubusercontent.com/<репо>/<sha>/<файл>`.
  Ни `Cache-Control: no-cache`, ни `?t=<штамп>` кэш не пробивают. Бонусом
  все файлы приезжают из одного коммита, и пуш в середине установки не
  смешает версии. Не удалось узнать хеш — качайте по ветке, но не
  падайте.

## 4. Ключ доступа

- Читайте ключ **из переменной окружения** и назовите её в README.
  Годится `GH_TOKEN`; своё имя тоже можно, но тогда его придётся
  прописать в goInstaller руками.
- Никогда не передавайте ключ аргументом команды. `/proc/<pid>/cmdline`
  читает любой локальный пользователь. Кладите его в конфиг `curl` с
  режимом 0600 и удаляйте файл сразу после запроса.
- Не печатайте ключ в журнал и не сохраняйте его в конфиг продукта в
  открытом виде без нужды.

## 5. Признак «уже установлено»

Один однозначный признак, который **не появляется раньше конца
установки**:

```bash
# хорошо: ключ пишется последним шагом
[ "$(json_get /opt/goproduct/config.json installed)" = "true" ]
# хорошо: бинарник на месте
[ -x /usr/local/bin/goproduct ]
# плохо: существование каталога или config.json
```

Каталог остаётся после неполного удаления, а `config.json` у половины
продуктов создаётся уже при выборе языка. По такому признаку оператор на
чистой машине получает разговор про обновление там, где обновлять нечего.

## 6. Где лежит код

Дерево установленного продукта — в `/opt/<продукт>`. Оттуда читается
версия, стоящая на сервере. Однофайловые продукты копируют себя в
`/usr/local/bin/<команда>` — это тоже годится, но скажите об этом: такой
скрипт нельзя запускать через `bash <(curl …)`, копия `$0` не получится.

Запишите ветку, с которой поставились:

```bash
printf 'branch=%s\nrepo=%s\n' "$BRANCH" "$REPO" > /opt/goproduct/.install-source
```

goInstaller берёт её как умолчание при обновлении. Без этого файла человек,
сидящий на стабильной ветке, уедет на отладочную одним промахом по Enter.

## 7. Порты: назовите их сами

Заведите `NEIGHBOURS.md` и опишите в нём каждый порт: протокол, адрес
привязки, режим, и **обязателен он или есть запасной вариант**. Три
уровня, которыми думает goInstaller:

| Уровень | Что значит | Пример |
|---|---|---|
| обязателен | без порта продукт не встанет | 443 у telemt в режиме pro |
| замечание | есть запасной вариант или необязательная часть | 853 у goDNS pro, дальше 8853 |
| к сведению | порт просто станет занят | 1986 у выключенного по умолчанию MCP |

Правила, нарушение которых ломает соседей:

- **Не занимайте чужое.** Список занятого соседями держите в
  `NEIGHBOURS.md` и сверяйтесь с ним до выбора порта.
- **Проверяйте занятость перед привязкой.** Половина продуктов серии
  этого не делала, и результат одинаков: служба молча уходит в цикл
  перезапуска, а человек видит «установлено».
- **Не убивайте чужой слушатель.** Спросите. goVLESS pro в режиме pro
  убивает любой не-xray процесс на 443 без вопроса, и это приходится
  отдельно объяснять оператору в проверке.
- **TCP и UDP различайте.** Занятый TCP 443 не мешает AmneziaWG на UDP
  443. Продукт, который пишет «443 занят» без протокола, отнимает у
  человека рабочий вариант.
- **Порты в контейнерах называйте предсказуемо.** При выключенном
  `userland-proxy` слушателя на хосте нет вовсе, и порт ищется через
  `docker ps`. Имя контейнера должно начинаться с имени продукта либо
  соответствовать общему неймспейсу, как `amnezia-awg<N>`.
- **Случайные порты** выбирайте из диапазона и **проверяйте** каждый
  кандидат. Обязательно запишите выбранное в свой конфиг: goInstaller
  читает его, чтобы не предлагать занятое соседу.

## 8. Режимы

Если режимов больше одного, назовите их идентификаторами и опишите, чем
они отличаются **по портам**, а не по маркетингу. У goAmnezia pro их три:
`pro`, `lite_site`, `lite`, и только первые два занимают TCP. Пара
«Pro или Lite» зашита во многих местах по привычке — не полагайтесь на
неё, если у вас иначе.

Назовите порт, без которого режима нет, прямо: pro у goAmnezia pro — это
AmneziaWG на UDP 443, и без него мастер ставит Semi-Pro. Если в
`NEIGHBOURS.md` такой порт записан как «желателен», goInstaller напишет
«готов» там, где режим не встанет.

Сценарий, который сам выбирает режим (Ленивый Pro у goAmnezia pro: итог —
pro или Semi-Pro), — не режим. В `config.json` пишите итоговый режим, а для
goInstaller дайте флаг без меню (`install.sh --lazy`), который загрузчик
передаёт дальше как есть: иначе человек отвечает на вопрос о режиме дважды.
Порядок пунктов и ответ на Enter goInstaller берёт с первого экрана вашего
мастера — меняете их, скажите об этом в `NEIGHBOURS.md`.

## 9. Мины bash, на которых подрывались все

Три грабли встретились в каждом продукте серии хотя бы раз. Проверьте свой
код на них перед релизом.

- **`… | grep -q` под `set -o pipefail` — с любым производителем.** `grep -q`
  выходит на первом совпадении и закрывает канал, производитель получает
  SIGPIPE, и статус ВСЕГО конвейера ненулевой. Успел он дописать или нет —
  гонка, поэтому ошибка плавающая. В goInstaller из-за `head | grep -q`
  скачивание установщиков проходило три раза из десяти, а из-за
  `locale -a | grep -q` на macOS меню каждый раз решало, что UTF-8 нет.
  Читайте вывод в переменную и ищите в ней, а первую строку файла —
  без конвейера:

  ```bash
  IFS= read -r first < "$file" 2>/dev/null || true
  case "$first" in '#!'*) ;; *) return 1 ;; esac
  ```

- **`local a="X" b="${!a}"` одной строкой.** bash раскрывает все правые
  части до присваиваний, поэтому `${!a}` получает пустое имя, а под
  `set -u` это обрывает весь скрипт. Ломалась любая установка на первой же
  строке функции запуска. Присваивайте раздельно.

- **`read -p` не разворачивает escape-последовательности.** Цвета в
  приглашении печатаются буквально: человек видит `\033[1mmain\033[0m`.
  В приглашениях цветов не ставьте.

## 10. Безголовый запуск

- При отсутствии терминала не блокируйтесь на `read`. Конец ввода — это
  **отмена**, а не согласие с умолчанием. Иначе автоматический запуск
  проходит мастер до конца на умолчаниях и перезапускает службу.
- Держите режим `--action=<имя> --json` или хотя бы набор переменных
  окружения для неинтерактивной установки. Ни один продукт серии этого
  пока не умеет целиком, и поэтому goInstaller после проверки просто
  отдаёт терминал мастеру.
- Ошибки печатайте в stderr. В stdout они попадают в `$(...)` вызывающего
  кода и ломают его молча.

## 11. Имена

Название продукта для людей — с «pro», строчными: `goVLESS pro`,
`goTelegram pro`. Так в `prod_name`, в сообщениях goInstaller, в README и
в постах. goVLESS долго стоял в меню без «pro»: имя писали руками, и
сверить было не с чем, теперь набор goInstaller это проверяет.
Идентификатор (`govless`), репозиторий и пути названием не считаются —
их не переименовывайте.

Всё своё начинается с имени продукта: systemd-юниты, файлы в
`/etc/nginx/conf.d`, каталоги состояния, записи в журнале, правила
межсетевого экрана. Проверьте, что таких имён нет у соседей. Совпадение по
смыслу не страшно: `godns-stats` и `gotelegram-stats` — разные файлы.

Чужое не трогайте: `sites-available/<сосед>` переписывается соседом
целиком, `/etc/letsencrypt/renewal/*.conf` не правится никогда, а
`acme.sh --install-cert` без повторной передачи путей молча стирает
настройки соседа, и поломка всплывает через два месяца.

## 12. Ворота системы

Назовите поддерживаемые версии ОС и архитектуру и проверяйте их **до**
установки чего бы то ни было. goAmnezia pro работает только на amd64,
goDNS pro требует Ubuntu 22.04 и новее, goTelegram pro — 24.04 и новее. Жёсткий список
версий не делайте: в день выхода следующей LTS установщик превратится в
бомбу.

`/etc/os-release` не подключайте через `source`: файл управляем извне и под
`set -u` затрёт ваши переменные. Разбирайте построчно.

## Как добавить продукт в goInstaller

В `go-installer.sh` правятся семь мест. Все они рядом и однотипны:

1. `PRODUCTS` — идентификатор в список.
2. `prod_name`, `prod_desc`, `prod_cmd` — имя (с « pro» строчными), одна строка описания,
   команда после установки.
3. `prod_installed` — признак из пункта 5.
4. `prod_ver_spec`, `prod_local_dirs` — где лежит версия в репозитории и
   на сервере.
5. `prod_repo`, `prod_entry` — репозиторий и файл-загрузчик.
6. `prod_ports` и при необходимости `prod_modes` — таблица портов из
   пункта 7.
7. `run_product_installer` — строка запуска с переменной ключа.

Дальше обязательно допишите проверки в `test_goinstaller.sh`: фикстуру
занятых портов для вашего продукта и ожидаемые коды. Набор гоняется без
сервера, на фикстурах, и падение в нём дешевле звонка покупателя.

И выдайте доступ к репозиторию продукта токену сводки версий
(`GOINST_READ_TOKEN` в секретах goInstaller). Сводку для всех серверов клуба
собирает GitHub Actions, и сборка падает, если у одного из продуктов не
видно веток: тогда сводка перестаёт обновляться у всех.

## Чек-лист перед первым релизом

- [ ] `<ПРОДУКТ>_VERSION` в начале строки, поднимается при каждом пуше
- [ ] ветки `main` и `dev`, ветка по умолчанию `main`
- [ ] переключение установленного с dev на main и обратно проверено руками
- [ ] загрузчик в корне, с shebang, работает по `curl` с заголовком
- [ ] файлы качаются по хешу коммита, а не по имени ветки
- [ ] ключ читается из переменной окружения, в argv не попадает
- [ ] признак «установлено» пишется последним шагом
- [ ] `.install-source` с веткой
- [ ] `NEIGHBOURS.md` с таблицей портов и тремя уровнями
- [ ] занятость порта проверяется до привязки, чужое не убивается
- [ ] конец ввода отменяет, а не соглашается
- [ ] нет `… | grep -q` под pipefail, нет `local a=X b=${!a}` одной строкой
- [ ] имена своих юнитов и файлов начинаются с имени продукта
- [ ] название для людей — `<Продукт> pro`, строчными, везде
- [ ] ворота ОС и архитектуры проверяются первыми
- [ ] запись о продукте добавлена в goInstaller и покрыта тестами
- [ ] токен сводки версий (`GOINST_READ_TOKEN`) читает репозиторий продукта

# Инструкции для AI-ассистентов

## Что это

goInstaller — один скрипт `go-installer.sh`, который ставит любой из шести
продуктов серии go (goVLESS pro, goTelegram pro, goDNS pro, goKaskad pro, goWARP pro,
goAmnezia pro) их собственными установщиками, а ДО этого проверяет ОС, порты
и соседей.

## Правила

- **Сам ничего не чинит и не настраивает.** Только проверяет и запускает
  штатный установщик продукта. Порты не освобождает, процессы не убивает,
  конфиги соседей не читает на запись.
  **Исключений четыре: размер пакета (MTU)**, решение заказчика 5.10,
  обновление пакетов apt на экране «Компоненты» и обновление Ubuntu до 24.04
  кнопкой «o» (оба — 14.10) и защита от сканеров (1.2.0, 02.11; правила ниже).
  Хостер отдаёт виртуалке 1500, а его сеть пропускает меньше (на
  177.3.218.172 — 1452). Тогда TLS до GitHub рвётся через раз: curl (28), то
  при опросе версий, то при скачивании установщика. `net_mtu_offer` при
  старте меню и `--install` (и командой `--net`) сравнивает карту с путём до
  GitHub и только по «1) Да» ставит размер, проверяет делом и записывает туда,
  где сеть настраивается (`/etc/network/interfaces` или netplan, по имени
  карты). Не прошёл полный пакет после правки — откат, ничего не записано.
  Без терминала — только сказать; отказ запоминается до нового размера.
  Узких мест на пути бывает несколько (там первый узел называл 1472):
  спускаться по ответам, а не верить первому. Адресов у GitHub несколько, и
  первый из DNS может не отвечать на большие пакеты вовсе (20.250.119.72 —
  только 56 байт): тогда предложения не было никогда, а `--net` всегда
  откатывал. Поэтому `net_mtu_pick` берёт первый из не больше трёх адресов,
  ответивший на DF-ping 1200 (две пробы на адрес — у api.github.com бывает
  один IPv4, и одна потерянная ICMP давала ложное «не отвечают»; общий
  потолок старта ~6 с, `GOINST_NET_PICK_MAX`), а проверка после правки — тот
  же `NET_IP`, две попытки. Адрес ответил при выборе и пропал при поиске —
  своя причина `lost`. Текст — «могут рваться», не «рвутся через раз»: на
  Aeza PMTUD работает. Правили или откатили при старте меню — «Нажмите
  Enter» до «Аркады» (`NET_CHANGED`), иначе старт не тормозим. Строка `mtu`
  в interfaces — с отступом соседних строк блока. Во время обновления Ubuntu
  размер не трогаем.
- **Компоненты: goInstaller обновляет только пакеты apt** (1.1.0, решение
  заказчика 14.10). Экран «Компоненты» (`c` в меню, `--components`) показывает
  версии системных компонентов продуктов — что стоит, что доступно — и
  обновляет отмеченные или все, только по выбору человека и подтверждению
  цифрой. Это второе исключение из «ничего не настраивает».
  - Таблица одна: `comp_spec` (главные пакеты, ещё пакеты группы,
    продукты). Её читают «Аркада», нумерованное меню, `--components`, тесты.
    Строка видна, только если главный пакет стоит. Пакеты к обновлению —
    стоящие пакеты группы и того же исходного пакета с кандидатом новее,
    кроме закреплённых (`apt-mark hold`). Закреплён главный пакет — вся
    группа стоит (`!`, не `↑`): родня без него разъехалась бы версиями.
    «Новее» — только `dpkg --compare-versions`; в наборе заглушка dpkg
    сравнивает по правилам Debian, иначе любая другая версия была бы
    «новее» и ошибку сравнения набор не увидел бы.
  - Сведения apt — одним `dpkg-query`, одним `apt-cache policy`, одним
    `apt-mark showhold` на все пакеты; внутри экрана — кеш, перерисовка apt
    не зовёт.
  - apt-get меняет пакеты в одном месте — `comp_apt_get`:
    `install --only-upgrade --no-remove` с confdef/confold, DPkg-замок 300 с,
    `NEEDRESTART_MODE=a` (оставлен решением заказчика 14.10: службы на
    обновлённых библиотеках перезапускаются сами; на подтверждении всегда
    строка об этом, в итоге — какие службы перезапустил needrestart). Никаких `upgrade`, `dist-upgrade`, `autoremove`,
    установки нового, `--allow-downgrades`. Без `--no-remove`
    iptables-persistent удалил бы ufw, без confold пропали бы правки
    nginx.conf goTelegram pro. Есть страж. Перед вопросом — пробный прогон
    `-s` с теми же ключами. Второе место — `osup_apt` обновления Ubuntu
    (правило ниже); страж разрешает его отдельно и только его четыре вида.
  - Движки продуктов (3X-UI, Xray, telemt, образы и модуль AmneziaWG, xray
    прокси API Telegram, accel-ppp, acme.sh, окружения ботов) — ТОЛЬКО
    показ: версия и кто обновляет. Обновление в обход продукта ломает
    совместимость (telemt вернётся к версии из config.json, образы закреплены
    по digest, goVLESS pro проверен со своей версией 3X-UI).
  - Окружение бота сломано, если его python не запускается или запускается
    не тот, что в `pyvenv.cfg`. С системным python3 НЕ сравнивать: goVLESS
    pro собирает venv на первом из python3.13…3.9, и после смены Ubuntu бот
    на оставшемся 3.10 работает — совет `rm -rf` там вредил бы. Замечание
    `✗` в `UD_PROB` (под меню и в сводке при входе), шаг — команда продукта.
    У goDNS pro чинить не через «снять бота»: пропадёт токен.
  - Образы AmneziaWG — только `.profiles.<p>.image_tag`, разбор JSON
    python3; рядом лежит откатный `.previous.image_tag`, и греп по строке
    выдавал старую версию за работающую.
  - `apt-get update` — с ограничением 180 с, замок 60 с, вывод в журнал
    `${GOINST_DIR}/logs` (0700). На экране — сам, если списки старше 12
    часов И прошлая попытка (`.apt-check`, удачная или нет) старше часа, и
    по `r`; в «Аркаде» в фоне. `u`/`a` её не ждут — прерывают и идут по
    прежним спискам. Фоновая проверка живёт только на экране «Компоненты»:
    уход с него, установщик, самообновление, выход и Ctrl-C
    (`ui_crash_exit`) гасят всё дерево процессов (`ui_comp_refresh_stop`):
    установщики продуктов сами зовут apt и упёрлись бы в замок списков.
    Фон — своя группа процессов (`set -m` в подоболочке `$( )`, номер группы
    — `UI_APTPID`). Стоп: STOP группе, снимок дерева (timeout уходит в свою
    группу, но остаётся потомком), TERM группе и дереву, CONT, до 0,5 с —
    потом KILL. Одним снимком дерева рождённое после снимка выживало (6-й
    круг). Итог уже записан (`rc`) — номер не трогаем: он мог достаться
    чужому.
  - Без терминала и без `--yes` — отказ до вопросов, как у `--uninstall`.
- **ОС проверяется так же, как продукт** (1.1.0). goVLESS pro отказывает
  ниже Ubuntu 24.04 / Debian 12 только при новой установке (нет x-ui или
  config.json — бесплатный Lite кладёт оба, pro поверх него не новая
  установка); goTelegram pro ниже 24.04 — только при первой установке;
  стоящий продукт строки ОС не получает. У goWARP pro предупреждения о
  новых Ubuntu нет: у Cloudflare есть resolute. goAmnezia pro на 20.04 —
  замечание: бот и сайт не встанут, AmneziaWG встанет. Препятствия ОС
  считаются отдельно (`PF_OSMUST`): мешает только ОС — итог называет
  систему, а не советует освобождать порты (и нумерованное меню не шлёт к
  карте портов). Если это Ubuntu 20.04/22.04, не контейнер, а на 24.04
  продукт по ОС проходит (`osup_hint_ok`: отказ goAmnezia pro по архитектуре
  обновлением не лечится), итог добавляет «обновить Ubuntu до 24.04 можно
  из меню goinstall — пункт o (или goinstall --os-upgrade)», карточка
  «Аркады» — «обновить Ubuntu: пункт o».
- **Обновление Ubuntu 20.04/22.04 до 24.04 одной кнопкой** (1.1.0, решение
  заказчика 14.10). Пункт `o` (и `щ`) — первым из служебных, только на Ubuntu
  20.04 и 22.04; Debian, 18.04, не-LTS, 24.04+ — нет (на 24.04 штатная
  программа предлагает 26.04, туда не идём: стоп строго по `VERSION_ID`). Есть
  состояние (идёт, прервано, итог не просмотрен) — пункт виден на любой
  версии. В контейнере — пункт есть, запуска нет. Третье исключение из
  «ничего не настраивает»: только по выбору, после предупреждения о бэкапе и
  подтверждения цифрой; курсор — на «Назад», Enter обновление не запускает.
  - Факты опыта (Aeza, 14.10): `do-release-upgrade -f
    DistUpgradeViewNonInteractive` из службы systemd без tty проходит без
    вопросов и сам не перезагружает; 20.04→24.04 — около 21 минуты и 3
    перезагрузки; на прыжке jammy→noble новые SSH-подключения минуты
    получают отказ; сторонние списки уходят в `*.list.distUpgrade` с прежним
    кодовым именем (на 20.04→22.04 — не трогаются); авто-пакеты
    `nginx-core`, `libnginx-mod-stream` сносятся как ненужные → nginx не
    стартует («unknown directive stream»); ufw удаляется на прыжке в 24.04
    (несовместим с iptables-persistent); venv ботов ломается; Docker с
    `--restart always` поднимается сам; пик диска около 4 ГБ.
  - Механизм — служба `goinstall-os-upgrade` (oneshot) зовёт КОПИЮ скрипта
    `os-upgrade/runner.sh --os-upgrade-run`, шаг за запуском, под `flock`
    (без него — по живому `run.pid`). Копия — ТОЙ ЖЕ версии: `$0` или
    `goinstall` с тем же `GOINST_VERSION`, иначе отказ до всего (старая не
    знала `--os-upgrade-run`, служба падала на каждой загрузке). Отметка
    шага — только после успеха; rc каждого шага; при сбое — `failed` без
    перезагрузки, служба выключена, apt.conf.d и `Prompt` возвращены. На
    каждом старте — восстановление dpkg (`dpkg --configure -a`, `apt-get -f
    install`). Перед `do-release-upgrade` — ожидание замка apt (до 15 минут):
    сам он замка не ждёт. Оборванный прыжок — один повтор. Больше 8 запусков —
    «круг перезагрузок». `Prompt=lts` всегда на время обновления. Числа из
    `state` — только цифрами (`osup_load` чистит).
  - **Машина шагов (второй круг 1.1.0, блокеры проверки).** Выпуск
    перечитывается после КАЖДОГО шага, меняющего пакеты (`_osup_pass`
    возвращает 10 — решить заново): dist-upgrade после обрыва по источникам
    noble сам доводил систему до 24.04, и следом звался do-release-upgrade —
    на 24.04 он ведёт на 26.04. `do-release-upgrade` зовётся ОДНОЙ строкой, в
    `osup_dru`, с последней сверкой выпуска (`osup_dru_ok`); есть страж. Код
    ошибки при выросшем выпуске (base-files ставится рано) — восстановление
    `force` и dist-upgrade; `dpkg --audit` пуст — дальше с замечанием в
    журнале, иначе `failed` без перезагрузки. Прыжок оборван после смены
    выпуска — восстановление, dist-upgrade, `reboot-required` → перезагрузка,
    и только потом отметка `rel-`. Перед прыжком `reboot-required` —
    перезагрузка до отметки «начат». `osup_reboot` в недонастроенный dpkg не
    перезагружает никогда; `systemctl reboot` не прошёл — `failed`. Повтор на
    выросшем выпуске разрешён (`osup_resumable`), начатый прыжок с выросшим
    выпуском при повторе остаётся начатым.
  - **«Идёт» — только при живом исполнителе** (`osup_alive`): служба есть и
    включена, или работает, или жив `run.pid`. Порядок в `osup_alive`:
    работает → `run.pid` → задание systemd → отметка `kick` (osup_start
    записал «идёт» меньше минуты назад и службу ещё не запустил) → и только
    потом `failed` и «включена без задания» = упал. Задание проверяется
    раньше `failed`: «Попробовать снова» ставит задание, пока служба ещё
    failed. Исполнитель не жив — `osup_load` показывает «прервано: служба
    обновления не работает» (state на диске не трогает): иначе запреты
    висели бы вечно. «Прервано» снимается: «Убрать отметку —
    обновлять не буду» (`osup_dismiss`, `--os-upgrade dismiss`): state →
    `state.failed-<время>`, служба и скрипт входа снимаются, журнал остаётся.
    Курсор экрана «прервано» — на «Назад». Шаг дольше часа и журнал не растёт
    20 минут — строка warn (`osup_stall`), ничего не убиваем.
  - Держатель замка (`osup_lock_holder`) — `find … -print -quit`, без
    конвейера: под pipefail исчезнувший посреди обхода процесс стирал
    найденного держателя.
  - До запуска: `apt-mark manual` стоящим пакетам групп `comp_spec` (кроме
    пакетов конкретного python), временный confold в apt.conf.d, снимок
    `before/` (пакеты, службы, контейнеры, ufw, порты SSH). Перед прыжком в
    24.04 при активном ufw и iptables-persistent — `netfilter-persistent save`.
  - Завершение на 24.04 — сбой пункта даёт замечание, не `failed`: SSH на
    прежних портах (первым; нет — перезапуск `ssh.socket`/`ssh.service`), источники
    продуктов `.distUpgrade` → `.list` с noble, если репозиторий его отдаёт
    (`osup_fix_lists`, выключается `GOINST_OSUP_FIX_LISTS=0`; чужие не
    трогаем), пропавшие пакеты групп ставятся снова (сторонние — нет:
    cloudflare-warp тянет 176 пакетов), упавшие службы — restart, DKMS,
    контейнеры, ufw. Что goInstaller сделает сам, экран предупреждения
    перечисляет отдельно — это входит в согласие на кнопку.
  - SSH сверяется по ФАКТИЧЕСКИМ портам (5-й круг): где слушал до (снимок
    `before/ssh` из `ss`), там должен и после — sshd или systemd на
    `ssh.socket` (`osup_ssh_ports <порты>`). После перезагрузки на 24.04 sshd
    не запущен, слушает только сокет; сверка по настройкам на сервере без
    строки `Port` давала ложное «не слушает 22». Настройки — запасной путь,
    когда снимка нет: `sshd -T`, без него — разбор sshd_config и drop-in по
    правилам sshd (ListenAddress с портом — свой порт, без порта — порты
    Port, по умолчанию 22).
  - Снимок `before/ssh` — только демон (`osup_ssh_ports --daemon`, 6-й
    круг): sshd с родителем 1 или MainPID `ssh.service`/`sshd.service`,
    systemd — на портах из настроек; loopback с портом не из настроек не
    берётся. Снимок пишется в сессии человека, а её sshd слушает пересылку
    X11 (127.0.0.1:6010) и `ssh -R`: после обновления «не слушает 6010»,
    перезапуск и красная тревога. Демона не узнали вовсе — снимок как
    прежде (все sshd), а не пустой: пустой увёл бы сверку к настройкам.
    Сверка «после» судит мягко (любой sshd): правка SSH может только
    убавлять перезапуски, не добавлять.
  - Перед сверкой — `sshd -t` (`_osup_sshd_test`): не прошёл — err
    «настройки SSH не проходят проверку», и SSH не перезапускается вовсе
    (перезапуск с битыми настройками уронил бы его). «Missing privilege
    separation directory» — не ошибка: настройки уже разобраны, а /run/sshd
    на 24.04 до первого входа нет. Перезапуск — `ssh.socket`, только если он
    включён или работает и не замаскирован, иначе `ssh.service`
    (`sshd.service`) — `_osup_ssh_unit`.
  - Уборка (`osup_cleanup`: прервано, снято, готово) зовёт `systemctl
    reset-failed`: без файла юнита служба висела бы в `systemctl --failed`.
    Изнутри службы reset-failed не действует, поэтому `--os-upgrade-run`
    при записанном прерывании (status=failed) выходит с 0; упавший
    исполнитель — не 0, это видит `osup_alive`.
  - Запуск из файла (`bash go-installer.sh --os-upgrade --yes`) делает
    `self_install` в `osup_flow` после согласия; скрипт входа зовёт команду
    по абсолютному пути `$GOINST_BIN` с проверкой `[ -x ]`.
  - apt-get исполнителя — только в `osup_apt` (update, dist-upgrade, `-f
    install`, `install --no-install-recommends --no-remove`). Есть страж.
  - Пока идёт — не ставим и не обновляем продукты, компоненты, себя (и
    `self_install` не пишет файл), не открываем меню продуктов (оба меню),
    не трогаем размер пакета (`--net` — отказ, при старте — молча), не
    удаляем себя.
  - Строки хода — первые `UD_OSUPN` в `UD_PROB`; в файл сводки таймер их не
    пишет, `--motd` берёт их вживую из состояния. Сводка выключена — ход при
    входе печатает временный `/etc/profile.d/goinstall-osupgrade.sh`
    (`$GOINST_BIN --os-upgrade status --short`, ранний разбор в `main`, без
    сети; только root и tty, `~/.hushlogin`; при включённой и записанной
    сводке молчит). Ставится запуском (строка в «goInstaller сделает сам» —
    часть согласия на кнопку), уходит после просмотра итога, при снятии
    отметки и при удалении goInstaller. `ui_badge` строку «✓ готово»
    замечанием не считает.
- **Защита от сканеров и ботов** (1.2.0, решение заказчика 02.11.2026,
  ТЗ `design/shield/SPEC.md`). Четвёртое исключение из «ничего не
  настраивает»: своя таблица nft, только по «1) Да» или из меню.
  - Списки — открытый `C24Be/AS_Network_List` (BSD-2, обновляется раз в
    сутки). **Ключ клуба туда не уходит**: `shield_fetch` зовёт `gh_curl -q
    --config` со своим файлом 0600 без заголовка ключа (страж). Хеш коммита —
    `api.github.com/…/commits/main` (без ключа 60 запросов в час на IP), файлы —
    `raw…/<sha>/…`; хеш не получен — по ветке.
  - Чужой список — чужой ввод: `_shield_py` (`python3 -I`, `ipaddress`)
    принимает только строгий CIDR; мусор, сеть шире /8 (v4) и /16 (v6),
    общий v4 меньше 300 строк, меньше половины прошлого или больше 3× —
    отказ всему списку, работает прошлый принятый. **Охват считается в
    адресах, а не в строках** (576 строк «все /8» — весь IPv4): после слияния

      Часы — 40 суток, дни — без срока, база адресов ≤ 200 тыс. (лишние —
      по давности, с запасом 5 %; вытесненные — в фильтр `gone`: вернулся —
      не «новый»), `naddr` — всего адресов. Снимок потоком: ≤ 60 МБ и ~1 с
      ЦП на 200 тыс. (`design/shield/bench/bench.sh`, тест — порог 64 МБ).
      Запись двухфазная: все `.tmp`, журнал `commit`, замены (meta
      последней); упали посреди — следующий снимок доводит по журналу.
      Снимки встали — сводка пишет «данные от …». Ошибка снимка — строка в
      журнал при смене текста, защите не мешает.
    - Владелец сети — `lists/owners` (сеть → AS → подпись) из
      `blacklist_with_comments.txt`, который уже качается; подпись — чужой
      ввод: `label()` (печатаемые, без управляющих и bidi, ≤ 60); хвост
      `NET-Name` режется до 400 знаков до регулярки (8 МБ одной строкой —
      < 1 с, REVIEW-6 №2). Новый
      файл — со следующим изменённым списком; файла нет — такт обновляет
      список сразу, не ждёт суток.
    - `stats/` 0700, файлы 0600, запись `.tmp` (O_NOFOLLOW) + `os.replace`;
      `stats` — ссылка: снимок и отметка через неё не пишутся (одна строка в
      журнал, `stlink=1` в status), сводка её не читает, `stats reset`
      через неё не удаляет. Не слетает: обновление,
      `shield_apply`, перезагрузка, `shield update`; `--shield remove`
      оставляет и говорит, как удалить; `stats reset` при снятой защите
      удаляет каталог, при стоящей — обнуляет (`base=1`: первый снимок
      только запоминает счётчики) и пересобирает таблицу.
    - Сводка `--motd` читает только `stats/summary` (готовые числа, каждое
      — цифры ≤ 15 знаков) и `stats/seen` («пока вас не было»: `at`,
      `upto`, `cin/cfw/csr`). Отметку пишет `_shield_sum_seen` только при
      показе скриптом входа (`GOINST_SUMMARY_SHOWN`) и root; отметка
      старше `started` (обнулили) не в счёт. Сканеры выкл — блок «Б» и
      `!1` в приглашении; тихая форма — только при вкл.
    - Всплеск — ≥ 2× медианы полных часов с начала счёта и ≥ 20; меньше 6
      таких часов — всплеска нет (на свежем сервере любой час был бы им).
      Часы и дни до начала счёта в sh-f — «—», а не 0.
    - Тесты — раздел «статистика (1.2.4)»: заглушка nft отвечает на `-a
      list table` из `$SFD/nfta` (генератор `nfa`, форматы 0.9.3 и 1.0.9)
      и с `NFT_STAT=N` не принимает уровень выше N. Сводка сверяется со
      строками `arcade_shield_*.json` (sh-a/b/c, 80/46, ru/en), sh-f —
      каркасом макета и числами.
- **Каждая строка таблицы портов снята с кода продукта.** Меняется
  продукт — меняется таблица (`prod_ports`) и README. Уровни: must —
  продукт не встанет или сломает соседа; soft — есть запасной вариант;
  info — просто станет занят.
- **Владелец порта — по systemd-юниту**, не по имени процесса: python3
  может быть панелью goDNS pro или goTelegram pro, nginx — сайтом goVLESS pro
  или goTelegram pro.
- **Ключ — только в окружение и конфиг-файл curl 0600.** В argv никогда.
  Страж в наборе смотрит ВЫЗОВЫ curl, а не упоминания слова: `command -v
  curl` рядом с `TOKEN_STATUS` однажды уронил проверку и скрыл бы
  настоящую утечку.
- **Ключ хранится в `/opt/go-installer/token` (0600, каталог 0700)** и
  проверяется при каждом запуске запросом к репозиториям продуктов.
  «Ключ валиден» и «ключ открывает нужное» — разные утверждения; годится
  второе. Непроверенный ключ не сохранять. При недоступном GitHub ключ не
  удалять: он не виноват.
- **`local a="X" b="${!a}"` одной строкой НЕ работает.** bash раскрывает все
  правые части до присваиваний, `${!a}` получает пустое имя, под `set -u`
  это обрывает скрипт. Так ломалась ЛЮБАЯ установка в
  `run_product_installer`, и ни один тест этого не видел, потому что запуск
  чужого установщика тесты не трогали. Присваивать раздельно.
- **Приглашения `read -p` не разворачивают escape-последовательности.**
  Цвета в проекте — литеральные строки для `echo -e`; в приглашении
  подтверждения они печатались буквально. В `confirm` и `read_line` цветов
  не ставить, есть страж.
- **goKaskad pro и goWARP pro запускать из файла**: они копируют `$0` в
  `/usr/local/bin`, из `bash <(curl …)` это не работает.
- **Печать таблиц — в stderr**, как и say/warn/err: через пайп потоки
  перемешиваются. В `printf '%-9s'` колонки только латиницей: он считает
  байты. Для колонок с кириллицей — `pad_to` (символы, через `str_len`).
- **Название продукта — с «pro», строчными, везде**: в `prod_name`, в
  текстах сообщений, в README и постах. goVLESS до 0.9.1 стоял в меню без
  него: имена писались руками, и сверить было не с чем. Страж в наборе ищет
  название без «pro» в строках кода; идентификатор (`govless`), репозиторий
  (`duboshin52/goVLESS`) и путь (`$HOME/goVLESS`) названием не считаются. Когда
  в одной фразе название и режим, режим называть словом: «goVLESS pro в
  режиме pro».
- **Скобки в русской и английской половинах `bi` сходятся одинаково.**
  Скобка, поставленная за кавычкой, достаётся обоим языкам: подсказка ключа
  goWARP pro печатала «(из группы)):». Есть страж.
- **Все вопросы — цифрами.** `confirm` печатает «1) Да / 2) Нет», буквенных
  `[Y/n]` в проекте нет. Две привычки в одном разговоре человек не держит.
- **Не спрашивать то, что уже записано.** Режим установленного продукта
  читается из его `config.json` (ключ `mode` у всех трёх), а не
  выясняется вопросом. Значение сверяется со списком режимов ЭТОГО
  продукта: чужое слово дало бы пустой набор портов и ответ «всё свободно».
- **Язык спрашивается первым экраном, а не угадывается.** По локали
  русским подписчикам доставался английский: штатная локаль сервера
  `en_US.UTF-8`, и её же нередко присылает SSH. `lang_startup` зовётся в
  `main` ДО проверки bash, ОС, root и ключа, только для меню и `--install`
  и только при tty; справочные команды не спрашивают, чтобы не ломать
  скрипты. Выбор пишется `lang_persist` ПОСЛЕ проверки root. Экран выбора
  сам двуязычный и отвечается цифрой. Порядок вызовов в `main` стережёт
  тест: перестановка вернула бы отказы на чужом языке.
- **Enter и Ctrl-D — разные ответы** (`read_line`, `_menu_read_key`).
- **Пункты меню объявляются ОДИН раз** в `MENU_ITEMS`
  (`menu_items_main`, `menu_items_product`), рисуются двумя способами:
  стрелочным экраном и нумерованным списком. Второго набора пунктов не
  заводить: разойдясь, они дадут пункт, видимый в одном режиме и
  недоступный в другом. Ключи пунктов проверяются тестом на совпадение с
  ветками обработчика — мёртвый пункт и дубль номера в меню уже случались.
- **Меню исполняется тестом, а не греппается.** `drive` в наборе жмёт
  клавиши и сверяет, что вызвалось: перестановка пунктов местами греп
  проходит зелёной.
- **Строки меню готовить заранее** (`menu_build_rows`), перерисовка —
  чистый `printf` от `\033[H` с `\033[K` на каждой строке. Не считать
  номера строк и не прыгать через `\033[NA`: в goDNS pro эта арифметика врала
  на единицу дважды и затирала соседнюю строку.
- **Колонка имени нумерованного главного меню не ест пояснения**
  (`menu_fit_widths 16 14 '[1-9]*'`): колонку имени задают только продукты,
  колонки состояния и «доступно» — по самому длинному значению (не шире 22 и
  16): с прежними 22 и 16 при «готов» и «—» описаниям на 80 колонках
  оставалось 14 символов. Подпись шире колонки строка кладёт своей раскладкой
  (имя целиком, состояние, пояснение — сколько влезет, `MENU_W_ROW`).
  Пояснения служебных пунктов (`MENU_SVC`) — в одной колонке и целиком:
  общей с продуктами, иначе за самой длинной подписью, иначе за состоянием.
  Обрезанное пояснение режется по слову (`cut_words`), не «продукты оста…».
- **Стрелочный экран — не всегда.** `menu_is_interactive` требует tty на
  входе и выходе, не-`dumb` TERM и окно выше меню; иначе нумерованный
  список. Проверять обе ветки.
- **Готовность в строке меню считает `preflight`**, тихо. Своей копии
  правил не заводить — она разойдётся с проверкой.
- **Режимов у продукта может быть больше двух.** Список — в `prod_modes`,
  от требовательного к скромному; `prod_readiness` идёт по нему и говорит
  «только <режим>», когда скромный проходит. Писать «pro или Lite» в общем
  коде нельзя: у goAmnezia pro режима три.
- **Пункт вопроса о режиме — не обязательно режим.** `prod_mode_choices`
  повторяет первый экран мастера продукта: у goAmnezia pro это Ленивый pro,
  pro, Semi-pro, Lite, и Enter — Lite, как у него. Ленивый pro — сценарий
  первой установки с итогом pro или Semi-pro: в `prod_modes` его нет
  (config.json его не хранит, готовность по нему не считается), на стоящем
  продукте его не предлагают, а запускается он флагом `--lazy` — это
  единственный безголовый путь в серии. Порт, без которого режима нет,
  обязателен: pro у goAmnezia pro — это AmneziaWG на UDP 443, и мастер без
  него ставит Semi-pro. С уровнем «желателен» проверка писала «готов» там,
  где pro не встанет. Контейнер AmneziaWG на машине — замечание, а не
  препятствие: продукт предлагает подхватить его вместе с людьми.
- **Режим из командной строки сверяется** (`mode_arg`): опечатка вроде
  `--check goamnezia Pro` раньше проверяла пустой набор портов и отвечала
  «всё свободно». Теперь — код 64 и перечень режимов.
- **Порт может держать контейнер.** При `userland-proxy: false` слушателя
  на хосте нет вовсе, и `ss` покажет порт свободным. `scan_docker` и
  `_docker_holder` закрывают этот случай; goAmnezia pro держит AmneziaWG
  именно так. TCP и UDP — разные порты: занятый TCP 443 не мешает
  AmneziaWG на UDP 443, и проверка обязана это различать.
- **Номер версии читается одной таблицей** (`prod_ver_spec`) и локально, и
  из ветки на GitHub. Второй способ разошёлся бы с первым, и совет
  «обновляться нечем» врал бы молча. Версии сравнивать через `sort -V`
  (`ver_newer`): строковое сравнение путает 0.9.0 и 0.10.0.
- **Смена ветки должна происходить на деле, а не на экране.** goVLESS pro до
  1.3.7 печатал «✓ Updated to latest dev», оставаясь на main: клон одной
  ветки не видел другую, ошибки глушились `|| true`. Исправление живёт в
  загрузчике goVLESS pro, а не здесь: попытка чинить его клон из goInstaller
  правкой `remote.origin.fetch` нарушала правило «конфиги соседей не
  трогаем» и убрана в 0.9.0, когда goVLESS pro починили у себя. После любого
  установщика `installer_postcheck` сверяет ветку и версию с выбранными:
  надпись продукта об успехе не доказательство.
- **Бесплатные версии из инструкций — не pro.** Узнаёт их `prod_free_edition`
  (печатает имя: Lite, Kaskad), экран строится по нему одинаково для всех.
  goKaskad: бесплатный Kaskad — та же `/usr/local/bin/gokaskad` без строки
  `KASKAD_VERSION=`; его правила без меток pro забирает себе с 2.12.
  goTelegram: бесплатный MTProxy — контейнер `mtproto-proxy` (владелец
  `mtproxy`, для установки goTelegram pro замечание, а не препятствие) и
  строка `docker inspect mtproto-proxy` в команде или в install.sh поверх pro.
- **Бесплатный Lite из инструкции — не goVLESS pro.** Он ставится в те же
  места (клон в `/opt/govless-installer`, `/opt/govless/config.json`,
  команда `govless`), и goInstaller принимал его за pro: «Открыть меню
  продукта» запускал меню Lite, а загрузчик pro «обновлял» клон Lite из
  репозитория Lite. Lite узнаётся по origin клона, по имени репозитория
  (`prod_free_lite`). Установленным он остаётся: порты и юниты у него те же.
  Для него статус «бесплатный Lite», первый пункт ставит pro поверх, команду
  Lite goInstaller не запускает, HEAD клона Lite умолчанием ветки не служит.
  Клон заменяет загрузчик goVLESS pro, а не goInstaller; оставшийся клон
  Lite ловит `installer_postcheck`. Имя «goVLESS Lite» в строках кода
  страж названий не пропустит — писать «бесплатный Lite».
- **`x-ui` — юнит любой 3X-UI, а не только goVLESS pro.** Панель из старой
  инструкции проверка звала «остатками прежней установки goVLESS pro» и
  запрещала ставить, хотя установщик pro такую панель оставляет и берёт себе.
  Владелец её портов — goVLESS pro, только когда он стоит (`_xui_owner`),
  иначе `xui` («3X-UI»). Для установки goVLESS pro это замечание
  `govless-foreign-panel`, а не препятствие.
- **Удаление goInstaller — только своё** (`goinst_uninstall`, 1.0.6):
  команды `goinstall` и `go-installer` (псевдоним и команда — только если это
  наш скрипт), каталог `GOINST_DIR`, таймер и скрипт входа сводки. Продукты и
  размер пакета сети не трогать. Ключ — выбор человека: goKaskad pro читает
  `/opt/go-installer/token` как запасной. Каталог с подозрительным путём
  (`/`, пустой) не удалять — `goinst_remove` отказывает. Без терминала и без
  `--yes` — отказ ДО вопросов: иначе первый же read получал конец ввода и
  команда выходила молча (так было в первой версии). Из «Аркады» удаление
  идёт после выхода из экрана (`UI_UNINSTALL` → `main`).
- **Ветку выбирает человек, а не умолчание в коде.** `ask_ref` печатает
  номера версий рядом с ветками; умолчание при обновлении — ветка из
  `.install-source`, иначе первая в `prod_refs` (стабильная). Молчаливый
  переезд со стабильной ветки на отладочную недопустим.
- **goKaskad pro 3 — в `dev`, 2.x — в `main`** (1.0.9). Ветка стоящего —
  `KASKAD_BRANCH` из `/etc/kaskad/config`, и только у 3.x: 2.x веток не знает,
  строка от прежней 3.x ветку не означает. Выбранная ветка уходит установщику
  в `KASKAD_BRANCH`. В «Аркаде» вторая ветка — `UD_DEVREF`, обновление
  стоящего — `UD_UPDV` по его же ветке; при стоящем с dev курсор выбора ветки
  на dev, иначе Enter откатил бы 3.x на 2.x. Ветку `k3` (заморожена) в выбор
  не брать — решение заказчика 13.10. Язык — `KASKAD_LANG` (иначе 3.x
  спрашивает снова и предлагает английский). Язык передаётся только при первой
  установке: 3.x ставит язык окружения выше записанного и запоминает, и
  обновление переписало бы выбранный человеком (а переход с 2.x — русский). Порты дополнительных функций
  3.x — `prod_ports_opt` (info, в проверке и карте портов, не в «НУЖНЫ»):
  панель, шлюз (порты протоколов по умолчанию и постоянные), сайт, сертификат
  на IP быстрой настройки на 80. Выбор ветки идёт после проверки портов,
  поэтому строки общие для 2.x и 3.x.
- **Лимит GitHub один на весь клуб.** Он составляет 5000 запросов в час на
  владельца ключа клуба, то есть на все серверы разом.
  - **Все обращения к API идут через `gh_get` и `_token_probe`.** ETag
    прошлого ответа уходит в If-None-Match, и ответ 304 в лимит не
    засчитывается: проверено, `x-ratelimit-used` на 304 не растёт.
  - **Хеш коммита запрашивается как `application/vnd.github.sha`**: 40 байт
    вместо 59 КБ.
  - **Версия для уже виденного коммита берётся из кеша** `<id>.<ветка>.sha`.
  - **Исчерпанный лимит — это состояние `limited`, а не «ключ плохой».**
    GitHub отвечает 403 и в этом случае, отличить можно только по заголовку:
    `x-ratelimit-remaining: 0` или `retry-after`. До 0.9.6 такой 403 стирал
    ключ на каждом сервере клуба, запущенном в тот час. До сброса (отметка
    `@ratelimit` в кеше) сеть не трогаем.
  - **Код ответа брать из `-w`, а не из кода выхода.** С опцией fail curl
    выходит с ошибкой на любой 4xx. Поддельный curl в тестах читает `fail`
    из конфига так же, как настоящий, иначе он спрячет ошибку.
- **Итог установки — одна проверка** (`installer_verdict`, 1.1.0): код
  установщика, встал ли продукт, не остался ли бесплатный, та ли ветка и
  версия. Её зовут `--install`, нумерованное меню (`installer_postcheck`) и
  шаг «Сверка» «Аркады» (`ui_run_installer`): до этого «Аркада» писала
  «✓ Проверено, версия —» после «Установка не закончена» продукта.
- **Свежесть списков apt — время последней удачной проверки**, а не mtime
  `*Release` (это время публикации на зеркале, при Hit не меняется):
  `update-success-stamp`, своя отметка `.apt-ok` удачного `comp_refresh`,
  `pkgcache.bin`. По нему и подпись, и автопроверка. Журнал apt — 0600.
  Отказ без терминала и без `--yes` — код 3 у `--components update` и у
  `--uninstall` (1 — ошибка apt).
- **Связь с GitHub — с повторами и объяснением** (1.0.7, решение заказчика:
  «максимальная отказоустойчивость, показывать что происходит и почему»).
  У подписчика 6.10 каждый запрос шёл 5–9 с и отвечал 200, а проверка ключа
  обрывала его через 5 с: «GitHub недоступен» при живом GitHub.
  - Все запросы к GitHub — через `gh_curl`: до `GH_TRIES` (4) попыток, паузы
    2, 4, 8 с. Повторяется только сетевой сбой (коды curl из `_gh_net_rc`) и
    временный ответ GitHub (5xx, 429, 408 по `-w`). Окончательный ответ
    (200, 304, 401, 403, 404, код 22 с fail) не повторяется.
  - Ожидание — в `gh_cfg_net`: 30 с на соединение, 60 на попытку
    (`GOINST_GH_CONNECT_TIMEOUT`, `GOINST_GH_TIMEOUT`). Своих
    `connect-timeout` в конфигах не писать — есть страж.
  - Медленный DNS (адрес дольше секунды) узнаётся один раз и закрепляется
    строкой `resolve` до конца запуска; только при IPv4-маршруте.
  - Метка «сети нет» (`GH_DOWN_FILE`): запрос, исчерпавший попытки, ставит её,
    и следующие запросы того же захода отвечают сразу. Без неё скачивание на
    мёртвой сети ждало 268 с (хеш ветки, потом файл), с ней — 134.
  - Что видно человеку: при скачивании — каждая неудачная попытка с тем, что
    качали (`GH_WHAT`), и причиной; при проверке ключа и опросе в нумерованном
    меню — «Попытка N из 4: причина. Жду ответа» (`gh_wait_report`, ждёт
    только свои PID); на заставке «Аркады» — строка о повторах; на экране
    ошибки и в `--key check` — причина словами (`gh_net_reason`) и сколько
    пробовали. «Связь неустойчива» — только если ответ в итоге получен.
  - Пока открыта «Аркада» (`UI_ALT=1`), сетевой слой ничего не печатает:
    строки легли бы поверх экрана. Сообщения самого curl глушатся в `gh_curl`.
  - Проверено через прокси, портящий связь до настоящего GitHub: медленно
    (6 с на запрос, как у подписчика) — 1.0.6 «не достучаться», 1.0.7 ответ за
    7 с; обрывы через раз — повторы видны, ответ получен; тишина — 135 с до
    честного отказа с причиной.
- **Опрос GitHub не должен задерживать меню.** Все запросы разом в фоне,
  тайм-аут на каждый, ответ в кеш со штампом времени; промах кеша тоже
  кладётся, иначе недоступная ветка опрашивается на каждой перерисовке.
  Без ключа опрос не делается вовсе: `ui_poll_start` и таймер меню «Аркады»
  проверяют `TOKEN` (вживую на Aeza до 1.1.0 «Продолжить без ключа» слало
  пачку curl раз в N минут), подпись «обновляются сами» без ключа не пишется.
- **Срок кеша решает «пора ли спросить», а не «можно ли показать».** Кеш
  версий живёт минуту (`VER_TTL=60`), но показ идёт через `ver_cache_get`
  без срока: иначе через минуту после опроса колонка версий пустела бы до
  следующего такта. `$(ver_cache_read …)` для показа не использовать, есть
  страж. Главное меню само опрашивает GitHub раз в три минуты
  (`GOINST_MENU_REFRESH`) и перерисовывается на месте: без `clear`, без
  выхода из `pick_menu`, с тем же курсором. Таймер — `read -t` с отсчётом
  от `SECONDS`, чтобы нажатия не отодвигали обновление. Код больше 128 у
  `read` — вышедшее время, а не конец ввода: спутать их значит выходить из
  меню каждые три минуты. В нумерованном меню таймера нет: построчный
  ввод оборвал бы набранное наполовину.
- **Стороннего движка меню не подключать.** `whiptail` есть в базе
  Ubuntu/Debian, но его рамка чужая рядом с меню продуктов, цветной
  колонки состояния он не умеет, а выбор возвращает в stderr — туда же,
  куда проект пишет журнал. `dialog`, `fzf`, `gum` ещё и требуют установки
  до первого экрана.
- Версия `GOINST_VERSION` поднимается с каждой правкой, которая едет на
  сервер: `self_install` сравнивает её со стоящей копией. Правка только
  `.github/` на сервер не едет и версии не требует. Номер, уже выложенный в
  любую ветку (и тестовую) с другим содержимым, не переиспользовать: на
  сервере с ним `self_install` решит «уже эта версия», и таймер защиты
  останется на прежнем коде (REVIEW-4 №1: 1.2.0 → 1.2.1). В наборе версия —
  переменная `GIV`, а не число в тексте. Номер поднимается у **каждой
  сборки на серверы** (К5-11, стенд 03.11: две сборки 1.2.4). Страховка с
  1.2.5: запуск **из файла** при том же номере сверяет содержимое (`cmp`) и
  ставит файл в goinstall («та же версия, другая сборка», строка в журнале
  защиты); копия таймера идёт за goinstall. Из канала тот же номер не
  сверяется (сети нет) — goinstall и копия не трогаются, остаются равны.
- **`self_install` не из файла ставит ветку ровно этой версии** (находка
  владельца 03.11.2026: `bash <(curl …/test-shield/…)` ставил main 1.0.12, и
  защите нечего было дать таймеру). `self_ref_find`: GOINST_SELF_REF,
  запомненная (`.self-ref`), dev, прочие по списку — не больше 30. К API —
  список веток с хешами голов (ETag); не дали список — ещё по запросу хеша
  на каждую свою ветку (до трёх). Версии — по началу файла с raw по хешу,
  ответ в кеше `.sha`; «скрипта нет» (404) — только на 10 минут
  (`GOINST_SELF_NONE_TTL`): raw свежего коммита бывает 404. Сбой пробы (5xx,
  сеть) — не «нет версии». Поиск идёт на глазах: строка «Ищу ветку…» и
  повторы списка. Эта версия в нескольких ветках с разным содержимым — не
  брать ни одну, назвать все (`goinstall --self-update <ветка>`).
  Не нашлась: goinstall есть — не заменять, сказать словами с причиной
  (лимит, сеть, ключ 401, ошибка, нет версии) и советом `self_fix_hint`
  (`goinstall --self-update <ветка>`, если ветка известна, иначе запуск из
  файла); тот же совет — в отказе защиты. goinstall нет — GOINST_SELF_REF,
  как раньше, кроме мёртвой сети (второй круг ожидания) и нескольких веток
  (таймер получил бы чужой код). Найденную ветку `self_refs` добавляет к main
  и dev (обновления), `--self-update` запоминает свою (main/dev — стирают),
  ветку, которой нет в списке GitHub, `self_fetch_versions` забывает.
  `.self-ref` — ветка того, что стоит в goinstall: поставили из файла или
  запасным GOINST_SELF_REF — запись стирается; тот же номер другой сборкой из
  файла — не трогается (та же ветка). **main догнал** (решение владельца
  04.11: апрув → тест-ветка → main): версия main в кеше не ниже и стоящей в
  goinstall, и лежащей в запомненной ветке — `_self_ref_caught` в
  `self_fetch_versions` стирает запись, обновления дальше из main; стоящая
  или ветка новее main, версии ветки нет (сбой пробы) — запись остаётся.
  «Аркада» и нумерованное меню обновляют из одной ветки — `self_best` (main,
  dev, запомненная); экран «Обновить goInstaller» называет её, `selfyes`
  зовёт `self_update <эта ветка>` (REVIEW-8 №3; до 1.2.5 «Аркада» брала
  только main). goinstall пишет `_self_put`: свой временный файл
  `goinstall.XXXXXX` рядом и `mv` — и из файла, и из канала, и в
  `self_update`.

## Меню «Аркада» (с 1.0.1)

- **Без ключа — «2 Продолжить без ключа»** (решение заказчика 14.10). Меню
  работает всё, кроме скачивания; установка и обновление (`wizard`,
  `continue`, `yes`) идут через `ui_need_key` на ввод ключа и после него —
  снова в мастер продукта. Так же, как нумерованное меню: режимы не должны
  расходиться. Эталон `k1` поправлен на одну строку пункта.

Макет — пакет Claude Design в `design/handoff`, решения заказчика поверх
него — `design/README.md`, и они сильнее пакета. Прежнее нумерованное меню
осталось запасным путём (нет tty, `TERM=dumb`, `GOINST_PLAIN_MENU=1`).

- **Экран — массив строк из сегментов «токен␟текст␞»**, суффикс `+sel` у
  токена — выделение. Одна строка печатается тремя способами: в цвет
  (truecolor, 256, 16, без цвета), в ASCII и дампом по клеткам. Дампом тест
  сверяет 25 экранов в двух ширинах и на двух языках с `spec/screens`
  клетка в клетку. Раскладку проверять эталоном, а не глазами; эталон
  «ЧТО НОВОГО» гасится (заказчик отложил), `v2` не рисуется.
- **`$VAR` вплотную к не-ASCII — только `${VAR}`.** bash в C-локали (и на
  macOS) считает ведущий байт UTF-8 частью имени: `"$UI_US╔"` — это
  переменная `UI_US╔`, и рамка рвётся. Есть страж.
- **Ширина считается в символах — нужна UTF-8-локаль.** SSH приносит
  `ru_RU.UTF-8`, которой на сервере нет, и bash считает байты.
  `ui_locale_fix` переходит на C.UTF-8, а без неё — на ASCII-рамки.
- **Никаких `производитель | grep -q` под pipefail — никаких, не только
  `head`.** `grep -q` закрывает канал на первом совпадении, производитель
  ловит SIGPIPE, конвейер «ложен». `locale -a | grep -q` на macOS отвечал
  «C.UTF-8 нет» каждый раз, и меню уходило в ASCII. Список — в переменную,
  grep — по ней. Страж смотрит все такие конвейеры в коде, а не одну строку.
- **Упавшее меню возвращает терминал.** Альтернативный экран и спрятанный
  курсор без возврата оставляют человека перед пустым окном. `ui_main`
  ставит ловушку EXIT (`ui_crash_exit`) и печатает, как открыть прежнее
  меню. Других ловушек EXIT в скрипте нет; появятся — сцеплять, не затирать.
- **Опрос не стартовал — меню, а не заставка.** Иначе заставка ждёт
  ответа, которого не будет.
- **Клавиши: цифры и стрелки на каждом экране.** На телефоне стрелки
  неудобны. Стрелки понимаются в обоих режимах (`\033[A` и `\033OA` — терминал
  остаётся в режиме приложения, если его не вернула прошлая программа).
  Русская раскладка `з к д г й` = `p r l u q`, кроме ввода ключа.
- **Пачка клавиш — не всегда вставка.** В 1.0.1 всё, что пришло за 10 мс,
  выбрасывалось как вставка, и «цифра, Enter» (привычка прежнего меню) или
  повторное нажатие, пока экран думал, пропадали молча: на 89.125.74.168
  «Выход» не выходил, меню казалось зависшим, человек перелогинивался.
  Теперь одна клавиша с Enter или повторами — это нажатие; пачка разных
  символов — вставка, и внизу экрана об этом сказано (`UI_NOTE`). Enter в
  течение 0,4 с после действия цифрой или буквой и после любой смены
  экрана глотается (`swallow`), пачка Enter — одно нажатие: иначе
  «цифра, Enter» в человеческом темпе или несколько Enter, нажатых, пока
  экран думал, проходили мастер насквозь до «Да, запустить установщик».
  Проверено в настоящем SSH-терминале на почасовом сервере: 1.0.1 на
  «0»+Enter пачкой не выходил, 1.0.2 выходит сразу.
- **bash на время `read -n` сам включает icrnl** — проверено на сервере с
  `stty -icrnl`: Enter из терминала приходит как `\n` и в «сыром» режиме.
  `\r` встречается только при вводе каналом; зато построчный `read`
  («Нажмите Enter») в терминале без icrnl ждал бы Ctrl-J, поэтому настройки
  терминала сохраняются до продукта и возвращаются после.
- **Экран отдаём продукту — потом сбросить ввод и сразу нарисовать.**
  После меню продукта и установщика набранное вслепую выбрасывается
  (`ui_flush_input`), прежний экран рисуется до пересборки сведений:
  `ui_model_load` занимает секунды, и пустое окно выглядело зависшим.
  Сама пересборка идёт одним сканом `ss` и `docker ps`
  (`scan_cache_begin`/`scan_cache_end`), а не на каждую проверку.
- **Раскладка по ширине:** от 80 — два окна, 46–79 — один столбец, меньше
  46 × 24 — экран «окно мало»; SIGWINCH пересчитывает на ходу.
- **Размер холста — выбор человека, F2 по кругу** (`ui_size_mode`, файл
  `/opt/go-installer/.ui-size`): `full` — во всю ширину окна, не шире 160, по
  центру; `center` — 80×24 по центру; `compact` — 80×24 в углу, как до 1.0.5.
  Высота в `full` остаётся 24: растянутые по высоте окна на 130×34 выходили
  пустыми коробками. Отступы добавляет только `ui_emit`, а `ui_dump` их не
  видит — эталоны клетка в клетку не меняются. Подсказка «F2 размер» — только
  когда окно шире 80. Шрифт скрипт не меняет, это настройка терминала.
- **F-клавиши:** F2 — размер, F3 — карта портов, F4 — язык. Понимаются
  `\033OQ` (xterm, iTerm, Termius), `\033[12~` (rxvt, PuTTY), `\033[[B`
  (консоль Linux). F1, F10, F11 не занимать: их перехватывают система и
  терминалы. Основной ввод — по-прежнему цифры и стрелки.
- **Замечание, которое меняет суть, называется своим словом.** goDNS pro
  при занятом 443 ставится рядом (DoH на 4443), и 443 в таблице — «к
  сведению»; меню писало «○ готов», и человек на сервере с goAmnezia pro
  читал это как «встанет на стандартный порт». Теперь правило
  `godns-beside-443` — замечание, в меню «◆ не на 443», а под строкой ИТОГ
  карточки — само замечание словами (`UD_VWHY`, первое `warn`/`err`
  проверки; под «✓ готов» не выводится).
- **Проверку считает `preflight`, экран только показывает.** Строки портов
  он кладёт в `PF_ROWS`, а пока стоит `PF_CAPTURE`, say/ok/warn/err
  дописывают сообщения в `PF_MSGS`. Второй логики «готов/не готов» для
  экранов не заводить.
- **Сводка при входе — единственное, что goInstaller оставляет на
  сервере**, поэтому только по согласию (вопрос один раз, при первом
  меню). Таймер `goinstall-watch` раз в 30 минут со сдвигом до 10, скрипт
  входа в `/etc/profile.d` только для root и tty, `~/.hushlogin`
  уважается, сеть при входе не трогается (`--motd` читает файл).
  `--summary off` снимает всё. «Сведения от» не должно врать: ничего не
  получили — время остаётся прежним. Есть новое или замечания — отсчёт на
  5 секунд (экран «Б» макета): Enter — `--motd` сам делает `exec` меню,
  вернув stderr терминалу (скрипт входа глушит его), так что работает и
  со скриптом входа прежних версий; другая клавиша или тишина — консоль.
  Уже набранный ввод отменяет отсчёт (`read -t 0`): иначе он съел бы
  первую букву команды, а перевод строки открыл бы меню. Хвост стрелки
  дочитывается, перед меню ввод сбрасывается. В скрипте входа `trap : INT`:
  без него Ctrl-C во время сводки обрывал и остаток профиля. Таймер
  переписывает скрипт входа, если он от прежней версии.
- **Порт контейнера — со стороны сервера.** `docker ps` пишет
  `0.0.0.0:8443->443/tcp`; держит на сервере 8443, а до 1.0.2 бралось
  число после «->». Клиент docker новее демона отвечает ошибкой «Maximum
  supported API version is X» — повторяем с `DOCKER_API_VERSION=X`, как
  goAmnezia pro. Не вышло — причина в `DOCKER_ERR` и в строке проверки.
  `docker-proxy`, которого docker не назвал, у стоящего продукта с
  контейнерами (`prod_uses_docker`) — замечание, а не запрет: иначе
  обновление goAmnezia pro упиралось в его же AmneziaWG на UDP 443.
  `docker ps` — с тайм-аутом 5 с (зависший демон вешал бы меню), диапазоны
  портов `1000-1002->1000-1002/udp` разворачиваются. Кеш сканов вложенный
  (`with_scan_cache`): конец вложенного кеша закрывал бы внешний.
  Опрашивать docker в самой `preflight`, а не только в `$(port_holders …)`:
  в подоболочке `DOCKER_ERR` посчитан и тут же потерян.
- **Служба продукта — только та, что стоит** (`unit_state`, 1.0.8).
  `prod_units` перечисляет все службы продукта, а ставятся не все: у
  goWARP pro `warp-svc` есть только в режиме 3X-UI, `warp-bot` — только с
  ботом. До 1.0.8 сводка при входе звала их отсутствие «не работает».
  Нет юнита — нет строки; выключен человеком — ○ без тревоги; тревога —
  только у включённого и не работающего.
- **Сертификаты — по карте продуктов** (`design/README.md`): владелец — по
  домену в `config.json`, подсказка — проверка его продукта. Команды,
  трогающие чужой сертификат (`renew`, `--force-renewal`, `revoke`,
  `--install-cert`), в подсказках запрещены, есть страж. Доменному меньше 3
  дней или истёк — `✗`, меньше 14 — `!`; IP-сертификат acme.sh панели Lite
  живёт ~6 дней, тревога — меньше 2.

## Сводка версий для клуба (GitHub Actions)

Решение заказчика 29.09: фон не ходит по репозиториям сам. Сотни таймеров
на одном ключе — это ещё и вторичный лимит GitHub (на частоту), а его
условные запросы не снимают.

- `.github/workflows/versions.yml` раз в час (в :23, не в :00 — там очередь
  GitHub) запускает `go-installer.sh --digest` из main — тот же код опроса, что у сервера —
  и `.github/versions-publish.sh` кладёт `versions.txt` в ветку `versions`
  (один коммит без родителей). Публикует при изменении, а без него — если
  прошлой больше 2 часов (`GOINST_DIGEST_HEARTBEAT`, 7200); сервер не верит
  сводке старше 12. Расписание GitHub на деле срабатывает раз в 3–9 часов,
  а не раз в час (`gh run list`, 10–14.10): при прежних 6 часах сводка
  доживала до 15 и серверы ей не верили; с 2 — худший случай 2 + 9,5 < 12.
- Сервер (`--watch`) берёт её `contents`-запросом с ETag: 304 лимит не
  тратит, проверено вживую. Сводки нет или она старая — спрашивает сам, но
  только стоящие продукты и себя, без проверки ключа по шести репозиториям.
  Открытое меню спрашивает напрямую: там важна точность.
- **Сводка принимается целиком или никак.** Каждое поле — по строгому
  образцу (значения идут на экран и в имена файлов кеша); не хватает
  хоть одного своего продукта — отказ. Незнакомый продукт пропускается:
  сводку собирает main, и новый продукт окажется в ней раньше, чем
  обновятся серверы, — отказ отправил бы весь клуб спрашивать самому.
- Сборка падает, если у продукта не видно веток: Actions тогда не публикует
  ничего, остаётся прошлая сводка. **Добавили продукт — выдайте токену
  сводки доступ к его репозиторию.**
- Токен сборки — секрет `GOINST_READ_TOKEN`, лучше отдельный fine-grained
  только на чтение, не ключ клуба. В логи он не попадает: ключ, как везде,
  в конфиге curl 0600.
- Ветка `versions` в выбор веток goInstaller не попадает: `refs_sort` берёт
  только main и dev.
- Файлы в `.github/workflows/` GitHub не принимает от токена без права
  `workflow` (у `gh` по умолчанию его нет): `gh auth refresh -s workflow`.
- Каждый запуск — около 7 секунд, но минута Actions (округление вверх): раз
  в час — около 720 минут в месяц из бесплатных 2000. Раз в полчаса было бы
  1440; заказчик выбрал раз в час.

## Перед коммитом

```bash
/opt/homebrew/bin/bash -n go-installer.sh test_goinstaller.sh
/opt/homebrew/bin/bash ./test_goinstaller.sh
```

Набору нужен bash 4+; штатный на macOS — 3.2, поэтому вызывать из Homebrew.
Стенд для тестов не нужен: порты, юниты, контейнеры, ОС и дерево `/opt`
берутся из фикстур, система не трогается.

«Аркада» проверяется настоящим циклом: `ui_main` читает клавиши из FIFO
(`nav` в наборе), по одной — следующая уходит, только когда цикл записал
предыдущую в журнал `GOINST_UI_TRACE` («клавиша экран продукт»). Пачкой
они читались бы как вставка. Нарисованные экраны пишутся в
`${GOINST_UI_TRACE}.draw`: после установщика ввод сбрасывается, и клавишу
надо подавать, дождавшись экрана (`%result`), а не угадывая время. Enter
сразу за цифрой проглатывается — в тестах перед осмысленным Enter пауза
(`@0.6`). Всё, что меняет систему, заглушено и пишет,
что вызвали; `systemctl` — заглушка в PATH и там, где зовут функции
сводки: на сервере с goInstaller набор не должен трогать настоящий таймер.

`check ! cmd` в наборе не работает: в `"$@"` знак `!` — имя команды, и
проверка краснеет всегда. Отрицание — `check neg cmd`; есть страж на сам
набор.

Прежний стрелочный экран фикстурами не проверить — его гонять в
псевдотерминале (`pty.fork`), подавая клавиши с паузами: на смене режима
чтения (построчный ввод против посимвольного) введённое заранее теряется.
